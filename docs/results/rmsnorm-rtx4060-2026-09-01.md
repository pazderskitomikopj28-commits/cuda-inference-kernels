# RMSNorm fresh rerun — RTX 4060 Laptop GPU

This report records a new measurement run collected on 2026-09-01 from the
`df44422673549335640d66f4f06caab71abbdfe6` source revision. It is separate from
the earlier 2026-08-30 and 2026-08-31 result notes, so the older numbers remain
available for comparison.

## Environment and protocol

- GPU: NVIDIA GeForce RTX 4060 Laptop GPU, compute capability 8.9, 8,188 MiB;
- memory bus width: 128 bit; L2 cache: 32 MiB;
- driver 591.74; CUDA Toolkit 12.4.131; MSVC 19.38; Release `sm_89` build;
- executable: `D:\DevTools\Builds\cuda-inference-kernels-rtx4060\Release\rmsnorm_bench.exe`;
- executable SHA256: `40726BCF4208953559C0A527139FACAC7206E53C09BC04CD4EFB23CC81F0964D`;
- primary shape: 4096 rows × 4096 hidden elements, epsilon `1e-5`;
- block size: 128 threads; 20 warm-up iterations and 300 measured iterations;
- each fresh process checked 16,384 output elements against the host reference;
- seven fresh processes were run for each variant (28 processes in total).

The four variants were launched as separate processes. Their order was rotated
between rounds to reduce the effect of clock state and adjacent-process order:

```text
two-pass → fused-scalar → fused-float4 → fused-half2
fused-half2 → fused-float4 → two-pass → fused-scalar
fused-scalar → two-pass → fused-half2 → fused-float4
fused-float4 → fused-half2 → fused-scalar → two-pass
two-pass → fused-float4 → fused-half2 → fused-scalar
fused-scalar → fused-half2 → fused-float4 → two-pass
fused-half2 → two-pass → fused-scalar → fused-float4
```

The command used for each process was:

```powershell
& D:\DevTools\Builds\cuda-inference-kernels-rtx4060\Release\rmsnorm_bench.exe `
  --mode fused-half2 --rows 4096 --hidden 4096 --block-size 128 `
  --warmup 20 --iters 300 --verify-samples 16384
```

Only `--mode` changes for the other three variants. The reported aggregate is
calculated from the seven per-process P50 values: mean, median, and nearest-rank
P95. The range is retained so that process-to-process variation is visible.

## Primary result

| Variant | Mean of process P50 (ms) | Median P50 (ms) | Nearest-rank P95 (ms) | P50 range (ms) | Logical GB/s at median | Maximum error |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Two-pass FP32 | 0.840987 | 0.840704 | 0.841728 | 0.840704–0.841728 | 239.474 | 4.116e-7 |
| Fused scalar FP32 | 0.573646 | 0.573440 | 0.574400 | 0.573184–0.574400 | 351.086 | 4.116e-7 |
| Fused `float4` FP32 | 0.577602 | 0.577536 | 0.578400 | 0.577360–0.578400 | 348.596 | 3.831e-7 |
| Fused `half2` FP16 | 0.291083 | 0.290816 | 0.292000 | 0.290720–0.292000 | 346.141 | 9.761e-4 |

Using the median process P50 of two-pass as the baseline, the speedups are:

| Comparison | Speedup |
| --- | ---: |
| Fused scalar FP32 vs two-pass | 1.4661× |
| Fused `float4` FP32 vs two-pass | 1.4557× |
| Fused `half2` FP16 vs two-pass | 2.8908× |

The fused kernels remove the intermediate inverse-RMS global-memory handoff and
one kernel launch. The `float4` path is close to the scalar fused path at this
shape; vectorized loads do not guarantee a win when reduction and instruction
throughput dominate. The `half2` path stores input, weight and output in FP16,
loads two values per thread, and keeps the square-sum and inverse-RMS
accumulation in FP32. It does not use Tensor Cores.

`logical_GBps` counts one input read, one weight read and one output write per
element: 12 bytes for FP32 and 6 bytes for FP16. It is a normalized comparison
quantity, not a claim about physical DRAM traffic or peak bandwidth.

## Hidden-size sensitivity

This additional sweep used three fresh `--mode all` processes per shape with the
same warm-up, iteration and verification settings. Values below are the median
of the three per-process P50 values; the sweep is exploratory and is not pooled
with the primary seven-process result.

| Shape (rows × hidden) | Two-pass FP32 (ms) | Fused scalar FP32 (ms) | Fused `float4` FP32 (ms) | Fused `half2` FP16 (ms) |
| --- | ---: | ---: | ---: | ---: |
| 4096 × 1024 | 0.094016 | 0.061440 | 0.060416 | 0.036864 |
| 4096 × 4096 | 0.840704 | 0.574144 | 0.577536 | 0.290816 |
| 4096 × 8192 | 1.686528 | 1.167360 | 1.166336 | 0.581504 |

Across the two larger shapes, FP32 fusion stays around 1.4–1.5× faster than
the two-pass reference, while `half2` stays close to 2.9× faster. The smaller
shape is more launch-overhead sensitive, so its normalized GB/s should not be
compared directly with the larger shapes.

## Nsight Systems and SASS evidence

Current-submission Systems-only profiles were collected with one warm-up and five
measured invocations per process. Nsight Systems reported six kernel instances:

| Profile | Kernel instances | Median kernel duration |
| --- | ---: | ---: |
| Two-pass FP32 | 6 `row_inverse_rms_kernel` + 6 `apply_rmsnorm_kernel` | 390.368 µs + 567.661 µs |
| Fused `half2` FP16 | 6 `fused_rmsnorm_half2_kernel` | 325.900 µs |

The launch-count difference is consistent with the fusion design. Profiler
instrumentation changes absolute timing, so the table above is mechanism
evidence; the uninstrumented CUDA Event measurements are the performance result.

`cuobjdump --dump-sass` on the same executable found three `LDG.E.128` and one
`STG.E.128` instruction in `fused_rmsnorm_float4_kernel`. The half2 kernel
contains `HADD2.F32` and `F2FP.F16.F32.PACK_AB`, consistent with paired FP16
storage and FP32 arithmetic before conversion back to FP16.
